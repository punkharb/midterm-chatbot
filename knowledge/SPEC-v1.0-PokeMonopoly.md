# Poke Monopoly — Specification v1.0

Thai title: โปเก โมโนโพลี · Former names: Pokémon Seller Showdown AI (spec v0.8) / Monster Monopoly (proposal, 9 Sep 2026)

Status: final specification for implementation; English edition of the agreed v0.9 with identical content. Not yet implemented or playtested. All game numbers are experimental baselines, not balance results.

Rights boundary: the assessed build uses original or appropriately licensed names and media. Pokémon-inspired terms are design references only and do not imply affiliation with the rights holders (unchanged from the proposal).

## 0. Changes from v0.8

| Topic | v0.8 | v1.0 | Reason |
|---|---|---|---|
| Name | Pokémon Seller Showdown AI | **Poke Monopoly** | Team decision |
| Decision model | An LLM picks an action ID and writes a short line | **Jev** (typesafe.ai, System One) answers typed questions only | Faster and cheaper, and it returns probabilities and confidence that code can act on |
| AI dialogue | Generated by the LLM | **Line bank** keyed by personality × situation × trust; Jev picks the line ID | Jev cannot generate text. **This contradicts the proposal's "generate brief dialogue", so the advisor must be informed** |
| Numbers | The model reads scores | The engine computes every number and sends named buckets | Jev is weak at maths, counting and numeric comparison |
| Latency | 4 s deadline per request | 1 s per request, 1.5 s per decision | An earlier live test measured 0.12–0.35 s, with one 1.8 s outlier |
| AI evaluation | 20 LLM games as a smoke test | 300 games with Jev in the loop | Input costs $0.042 per million tokens and output is free |
| Document structure | Ordered by game system | Organised by the four responsibilities: Specify / Harness / Verify / Control | Applies the agentic-engineering framework |
| Development method | Not specified | AGENTS.md + skills/ + CI for the team and coding agents | "Decide it once, in a file" |
| Unspecified cases | Scattered through the text | "Decisions you never made" table (§3.1) | Unspecified behaviour means the AI decides for you |
| Plan | 12 weekly rows | 6 cycles × 2 weeks with dated milestones, exit criteria and cut lists | Checkable, and decisions land on time |
| Game rules and content | §4–§8 | Unchanged; condensed in §4 and Appendix A, except content is now tiered core/target and Standard 3 Laps opens after playtest | Keeps the agreed rules; the two exceptions align with the proposal |

## 1. Goal, hypotheses and success criteria (Specify)

A single-player web board game in which one human plays against 1–3 AI opponents on a 24-space loop.

- **Catch:** players catch Pokémon with Balls.
- **Keep or sell:** each catch is kept for its Ability, for battle or to evolve, or sold when passing Start.
- **Social play:** players use items and chat or bargain with opponents that remember what happened in the game.
- **Win:** the player with the most coins wins.
- **Setup:** each AI's class, personality and difficulty are set before the game.

What must be proven:

- **H1 Fun:** keep-or-sell, Ball choice and attacking are decisions players genuinely hesitate over.
- **H2 Personality:** personality, chat and memory observably change what the AI does.
- **H3 Engineering:** Jev lets the AI decide on time, 100% legally and at controlled cost, while the rules stay auditable.

| Criterion | How measured | Type |
|---|---|---|
| `illegalAppliedActionCount = 0` | Every test, sim and playtest | Hard gate |
| Hidden-info leaks = 0 | Adversarial set (§8) | Hard gate |
| A game can finish with Jev off or down, with 1, 2 and 3 AIs | Tests + kill switch | Hard gate |
| Total AI spend ≤ THB 1,500 | Usage log | Hard cap |
| AI decision time per turn p95 ≤ 2 s | Telemetry | Target; report actuals |
| Players can tell an opponent's personality from its behaviour | Playtest with 5–8 people | Report; no claim of statistical significance |
| Personality or messages change choices in controlled scenarios | Eval set | Report with n and effect size |

### Delivery scope

- 1–3 AIs, 2–4 seats in total. Quick 2 Laps is core; Standard 3 Laps opens once playtest confirms the session length is acceptable.
- 6 core classes with passive abilities; Team Rocket and Collector are stretch goals after G2.
- Content is tiered: core is the starter lines of the 6 classes; the target is 19 base species with evolution lines and Abilities.
- 3 Ball types, 7 utility items, one board and 6 events. No Market, Buyer or Trend.
- 4 personality presets. Easy and Normal are core; Hard depends on gate G2.
- Short chat, instant-trade Deal Cards, and one promise type (`no_attack`).
- Local save, log export, replay, simulation, eval set and user playtest.
- **Out of scope:** multiplayer, accounts, voice, campaign, a full battle system, database deployment and public hosting.

### Adaptations from the original video concept

- **Kept:** the loop of moving, catching, selling, battling and evolving.
- **Changed:** it becomes a 24-space web board that ends after a number of Laps instead of 8 rounds.
- **Removed or moved:** Market, Buyer and Trend are cut, and all selling moves to Start.

If the vertical slice is not fun, fix the loop first. Do not force-tune numbers to get the graph we want.

## 2. Engineering principles: the four responsibilities

AI writes more of the code and makes more of the in-game decisions, but the team still defines what the system must do and owns the outcome.

| Responsibility | In the game (AI opponents) | In development (team + coding agents) |
|---|---|---|
| **Specify:** what should it do? | Rules in §4, criteria in §1, decisions register in §3.1 | Spec first. Every PR cites a spec section. A rule change updates the spec and its tests together |
| **Harness:** what can it use? | Context = role-scoped state; tools = legal action IDs from the engine; rules = personality rubric files | AGENTS.md, skills/, and test/sim/eval scripts agents can run themselves (§7) |
| **Verify:** did it work correctly? | Tests → eval set → critic (exploit sims) → human playtest (§8) | CI on every PR; offline Jev fixtures |
| **Control:** what is it allowed to do? | Token budgets, kill switch, least privilege; the engine is the sole arbiter (§9) | Agents hold no API key, work on branches, and a human reviews before merge |

## 3. User flow and screens

Home → choose Quick/Standard → choose class → choose 1–3 AIs → set each AI's class/personality/difficulty → review setup → roll for first player → play → results

**Setup**

- Random All and presets for a quick start.
- Classes are unique within a game; class and personality are independent.

**Turn order**

- Seats are fixed before the roll. The highest roller starts, then play follows seat order.
- If the top roll ties, only the tied players re-roll.

**Board screen**

- Arrows and turn-order numbers.
- Team cards, our items, opponents' coins/position/team, opponents' item counts, chat and the event log.
- Catch and win chances, and item effects, are shown before confirming; every number comes from the engine.

**AI turns**

- The AI speaks briefly at significant moments. Lines can be skipped and turns sped up.
- The game can be finished without ever typing in chat.
- A "Backup bot mode" badge shows truthfully whenever an AI is using the fallback.
- The player-facing UI and line bank are in Thai; UI strings in this document are given in English.

### 3.1 Decisions you never made

Every case needs a test that can actually reach it ("You cannot test what you cannot reach").

| Situation | Specified behaviour |
|---|---|
| Only one legal action (e.g. must roll) | The engine applies it automatically without calling Jev |
| Shortlist empty after personality filtering | Include at least one option per legal action kind; if still empty, skip |
| Pokémon found but no Ball | The only option is to release; the catch button is greyed out with the reason "No Ball" |
| Not enough coins for anything in the Shop | Items are greyed out with "Not enough coins", plus a skip button |
| Jev times out, returns 429 or errors mid-deal | The fallback policy decides under the same concession budget; the deal does not commit until re-confirmed |
| Jev's answer is not among the options, or the revision does not match | Discard the answer, use the fallback, and log `fallbackReason` |
| Confidence below the floor | Apply the rule in §5.6 |
| Every AI is in backup mode | The game continues with a single banner |
| The player types something unclassifiable (emoji, slang) | intent = `other`; the AI replies with a neutral line and tactics are unchanged |
| A message tries to make the AI break rules or reveal hidden information | Reply with a "not falling for it" line; willingness and trust are unchanged |
| The browser closes during an AI turn | Resume from the last committed action; cancel the pending request and ask again; never start a new turn |
| Team is empty after the Sell Phase | Create a Rescue Starter (§4.5) |
| Event deck runs out | Reshuffle the discard pile |

UI house rules (kept as `skills/ui-rules/SKILL.md`):

- No blank screens: there is always a message.
- Say what to change, such as the budget or the target.
- An unusable button is greyed out and says why.
- Plain tone, no jokes.
- Every number comes from the engine.

## 4. Game rules (Specify)

All content tables are in Appendix A.

### 4.1 Setup and board

- **Board:** 24 spaces, made up of Start 1, Wild 11, Event 5, Shop 4 and Gym 3 (spaces 6/12/18).
- **Starting kit:** 20 coins, the class Starter, 5 Poké Balls and 1 class item.
- **Hidden information:** the starting kit is public; utility items gained later are secret.
- **Start income:** passing or landing on Start by movement pays 5 coins, once per pass. Nothing is paid at setup.

### 4.2 Turn structure and action budgets

Turn order:

1. **Start:** reset budgets and apply start-of-turn passives.
2. **Social window:** talk to one opponent per human turn. This does not cost the tactical action.
3. **Strategy:** use pre-move Abilities and one utility item or PvP, or skip.
4. **Move:** roll a d6 or use an Ability that replaces the roll. Slowing effects clear after the actual move.
5. **Start crossing:** collect 5 coins, add 1 to `creditedLap`, reset Abilities, then open the Sell Phase before resolving the destination space.
6. **Resolve:** reveal the space. If a Pokémon appears, spend 1 Ball or release it.
7. **End:** close expired effects and settle promises that are due.

Each turn has three budgets. They do not accumulate, and inventory and cooldown are checked separately:

- `tacticalAction = 1`: a utility item or PvP.
- `catchAttempt = 1`.
- `pokemonAbility = 1`.

**Social window**

- One offer plus at most one counteroffer, or one general message plus one reply.
- The game pauses only inside this window.

**Who starts conversations (MVP)**

- The human starts conversations; the AI replies or counters.
- There is no AI↔AI conversation, but attack history is kept for every pair.

### 4.3 Catching

- `d6 + classBonus + ballBonus + abilityBonus + itemBonus >= catchDC`. The roll is snapshotted after every party confirms modifiers and before rolling. Battle stats are not part of the catch formula.
- Every attempt consumes 1 Ball, success or failure. With no Ball the Pokémon must be released. The UI shows the success % for every Ball type held.
- Main Character's first-catch bonus is used whenever a real roll is made, even on failure. Skipping an encounter does not use it.

### 4.4 Combat, Gym and Tired

- Combat = `d6 + highest battle among non-tired members + classBonus + abilityBonus + itemBonus − debuffs`. Both sides confirm Abilities and reactions before the snapshot. No modifier may be added after seeing the result, except Porygon's reroll.
- **PvP:**
  - Both sides need a battle-ready Pokémon. Any opponent may be targeted regardless of distance, and it costs the `tacticalAction`.
  - The target may accept or decline. On a decline, the challenger loses the action but no coins.
  - Chat can change willingness but never legality.
- **Forced PvP sources:** only Battle Ticket, Rival's passive (once per Lap), or an Ability with `forcePvP`. If the target has no battle-ready Pokémon, the action is illegal.
- **Battle Reward:** the winner takes up to 6 coins from the loser, or evolves one eligible Pokémon by one stage (the loser then pays nothing). A tie gives no reward.
- **Attack counting:** declaring a challenge always counts as an attack attempt, even when declined or shielded.
- **Shields and Nurse Joy:** they block coin loss but never create coins for the winner. If Nurse Joy's passive already blocks the loss, no shield is consumed.
- **Gym:**
  - DC 5/7/9 in space order; a battle-ready Pokémon is required.
  - A win gives 1 badge, then a choice of 6 coins or a one-stage evolution.
  - A loss pays up to 3 coins. The Gym can be re-challenged on a later landing.
  - Badges only break ties; they are never worth coins.
- **Tired:**
  - A tired Pokémon does not count for battle and sells at ×0.8.
  - It expires at the end of the owner's next turn. Re-applying keeps the later expiry.
  - Event e5 targets the highest printed battle, with instance ID as a stable tie-break.

### 4.5 Pokémon: encounters, Abilities, evolution and Starters

- **Encounter pool:** 15 species, excluding the 3 starters and Porygon. Rarity weights are 50/33/17, uniform within a rarity. Repeats are allowed and each gets a new instance ID. Rarity is the `rarity` field only.
- **No team cap in v1:** every attempt already costs a Ball.
- **Abilities:**
  - Once per instance per Lap, reset when the owner passes Start.
  - Each player may activate at most one Ability per `globalTurnNo`, including reactions as defender.
  - An Ability that starts PvP also costs the `tacticalAction`.
  - An Ability that targets an opponent with a harmful effect is a `hostileAbility`.
  - Evolution does not reset cooldowns.
  - The engine supports only these effect primitives: fixedMove, moveDebuff, rollBonus, forcePvP, shield, heal, gainBall, peek.
- **Evolution:**
  - If the next form has a definition, use that form's stats and Ability.
  - Otherwise use Battle +2, Base Sale `round(current×1.5)` and the existing Ability.
  - No new systems may be added during evolution. Status follows the UID to the new form.
- **Original Starter:** sellable, with its price normalised to 5 coins for every class while it is still the base form.
- **Rescue Starter:**
  - Created when the team is empty after the Sell Phase commits: the class's base Starter with a new UID.
  - `saleValue = 0`; it skips every class bonus, cannot be traded, and cannot be resold in the same phase.
  - The rescue flag persists through evolution.

### 4.6 Items and Events

**Holding limits**

- Balls sit in a counted Ball Pouch; up to 4 utility items can be held.

**Shop**

- Always shows all 3 Balls plus 2 distinct random utility items.
- Buy at most 1 unit or skip; no refresh.

**Hostile items: Repel, Sticky Web, Pickpocket and Battle Ticket**

- They cannot target yourself and can target anyone regardless of distance.
- Pickpocket needs the target to have coins to take.
- Battle Ticket needs a battle-ready target.

**Slowing effects**

- The same kind does not stack, and cannot be applied to a target that still has that kind pending.
- With both kinds pending: `steps = max(1, min(d6 − 2, 2))`.
- They clear after the actual move, not at StartTurn.

**Price Shield**

- Blocks one whole hostile action and is then consumed.
- The declaration still counts against a promise.

**Events**

- e1: find a Pokémon, using any remaining `catchAttempt`.
- e2: +6 coins.
- e3: pay up to 4.
- e4: random item; a full hand receives a Poké Ball instead.
- e5: the highest-battle Pokémon becomes tired.
- e6: the poorest player(s) receive 5 coins, split and rounded down.

**Deck and randomness**

- The deck is shuffled at setup. All randomness lives in the engine and is logged.

### 4.7 Selling at Start, Laps and game end

1. **Order when passing Start:**
   - +5 coins
   - `creditedLap` +1
   - reset Abilities
   - Sell Phase (sell any number at once)
   - Rescue Starter if the team is empty
2. **Sale price:**
   - `saleBasis`: Rescue = 0; an Original Starter still in base form = 5; everything else uses the Base Sale of its current form.
   - A tired Pokémon uses `round(saleBasis×0.8)` before the class bonus.
   - Class bonuses apply only in the Sell Phase at Start.
3. **Game end:**
   - When the first player reaches the Lap target, announce the Final Table Round and play until every seat has had the same number of turns.
   - Remaining Pokémon are then auto-sold at `round(saleBasis×0.5)` with no class bonus.
   - Rescue Starters and items are not converted to coins.
4. **Winner:** most coins. Ties go to badges, then co-winners. Pokémon or evolution counts are never used as a tie-break.

### 4.8 Chat, Deals and Promises

**Chat**

- Topic buttons: ask for a truce / offer a trade / point at the leader / ask them to use an item / ask them to hold an item. Free text is up to 280 characters.
- Asking for a specific item never makes the engine reveal whether the AI holds it.
- **The hard line:** messages may change only the AI's intent in choosing action, target, item and willingness. They must never change coins, assets, Deal Card terms, dice results or legality.
- Loose talk is not a contract, and the UI must show when something is only words.

**Deal Card**

- **Formats:** one Pokémon ↔ coins, one item the owner chooses to reveal ↔ coins, Pokémon ↔ Pokémon.
- **Hidden items stay hidden:** no "any item" requests for secret items, and the AI never sees an opponent's other items through any channel.
- **Legality and willingness are separate.** The engine checks legality; willingness is the AI's own judgement.
  - Legality: assets really held, enough coins, items ≤4, no duplicate UIDs, quota remaining, matching revision.
  - Willingness: what is gained and lost, plans, personality, trust, messages.
- **Concession budget:**
  - `concession = max(0, netValue(given) − netValue(received))`, using one coin-equivalent valuation for every asset type.
  - It is charged to the budget only on commit.
  - Baseline: ≤2 per deal and ≤3 per game.
  - If late-game refusals spike because the budget is spent, trial a regenerating budget of 1 per Lap, capped at 3, via content config.
- **Item value:** an item with no legal use window left is worth 0.
- **Deal limits:** at most one successful deal per Lap per player (counting both sides) and counter depth ≤1. No partial transfers. Commits are atomic after a re-check.
- **The human always confirms their own deals.**

**Promise `no_attack`**

- **What is promised:** no PvP declaration, hostile item or hostileAbility against the recipient, from confirmation until the end of the promiser's next turn.
- **Activation:** the recipient must accept before it is active. It does not cost a tactical action.
- **Limits:**
  - One promise per directed pair.
  - No renewal.
  - Not created if its duration would run past game end.
- **Effect on trust (clamped to −3..3):**

| Promise outcome | Effect on trust |
|---|---|
| Broken (including when a shield blocked it; judged from the actual event actor/target) | −2 |
| Kept, with a real chance to attack | +1 (max +2 per pair per game) |
| Kept, with no chance to attack | 0 |
| `closed_by_game_end` | Excluded from the kept/broken ratio |

- **Privacy:** whether an attack was possible is private information. The promise button does not depend on holding a hostile item, so it does not leak cards.
- **Memory UI:** shows evidence from real events, e.g. "Broke a promise on turn 5".

## 5. AI opponents with Jev (Harness)

### 5.1 Jev: verified facts

- **Docs and npm:** checked on 2026-09-30.
- **Latency figures:** from an earlier live test on 2026-09-16/17 that did not record its network location.

Sources:

- https://docs.typesafe.ai/models.md
- https://docs.typesafe.ai/api.md
- https://docs.typesafe.ai/model-jaggedness/jev-1.13.md
- https://docs.typesafe.ai/confidence.md
- https://www.npmjs.com/package/@typesafe-ai/sdk

| Topic | Value |
|---|---|
| What it is | A System One model for decisions inside software. It returns typed answers with calibrated confidence and **does not generate text** |
| Endpoint | `POST https://api.typesafe.ai/v1/systemone`; body `{model, state, questions}`; `Authorization: Bearer` header |
| Question types | **Choice** (≤255 options → `choice`, `probabilities`, `confidence`), **Score** (2–10 levels), **Noul** (yes/no → 0–1). Several questions can go in one request |
| Model | `jev-latest` → `jev-1.13.0`. **Pin `jev-1.13.0`**, because the alias moves when a new release ships |
| Price | $0.042 per million input tokens; output is free |
| Rate limit | 40 requests/s and 100K tokens/s; the docs say these are "adjusting dynamically" |
| Context | 64k tokens per request; state plus the longest question ≤32k |
| Measured latency | 123–348 ms per request; one outlier of 1,795 ms (re-measure from a Thai network in C1) |
| SDK | `@typesafe-ai/sdk` 0.6.0 (TypeScript), used server-side only |
| Weaknesses the docs acknowledge | Literal reading, maths and counting, indirection, cluttered state, adversarial content, non-English text (**Thai untested**), text generation |

### 5.2 Division of labour

| Part | Does | Must not |
|---|---|---|
| **Engine** (code) | Rules, RNG, every number (odds, netValue, trust, concession), legal actions, shortlist, validation, commit | Make network calls |
| **Jev** | Choose among the engine's options, classify chat, decide keep-or-sell, pick lines | Modify state, see anything outside its role, compute numbers |
| **Line bank** (content) | Thai lines written by the team, with slots the engine fills with names and numbers | Invent new text during play |
| **Fallback policy** (code) | Personality-weighted utility, used when Jev is unavailable or not confident enough; also the "policy-only" baseline | Use hidden information |

### 5.3 Decision points → questions

| Decision point | Question | Options / how results combine |
|---|---|---|
| Strategy | Choice | Shortlist of ≤12 legal action IDs including `skip`, filtered by personality without removing any action kind entirely |
| Encounter | Choice | Balls held + `release`, with success-chance buckets and remaining counts |
| Sell Phase | One Noul per Pokémon | "Should `team[i]` be sold now?"; code sells those with `noul ≥ threshold(personality)` |
| Challenged to PvP | Choice | `accept` / `decline` |
| Reaction Ability | Choice | Legal reactions + `none` |
| Battle / Gym reward | Choice | `coins` / `evolve:<uid>` for each eligible Pokémon |
| Deal response | Choice | `accept` / `reject` / `counter`, asked only when the concession is within budget; over budget, code rejects without calling Jev |
| Promise response | Choice | `accept` / `reject` |
| Chat intent | Choice + Noul | intent ∈ {truce, trade, point_leader, use_item, hold_item, threat, small_talk, other}; Noul "does it try to make you break rules or reveal hidden info?" |
| Line | Choice | ≤5 line IDs, pre-filtered by code for situation and trust |

- **Fan-out:** bundle every question of one decision point into a single request, including speculative ones such as the line after the action. The budget is at most 3 requests per AI turn.
- **Chat effect:** chat intent shifts next turn's target and item weights by a bounded ±1 bucket, applied by code.
- **Manipulation gate:** a message whose manipulation Noul exceeds its threshold **never enters `recent_chat`** for later decisions. The check gates the text rather than merely labelling it.

### 5.4 Rules for writing state and questions

Kept as `skills/jev-questions/SKILL.md`.

- **Role-scoped:** send only what that seat can really see.
  - Public: board, coins, teams, Lap, ability readiness.
  - Own: hand, Balls, peek results, interactions.
  - Never: Event order, opponents' secret items or RNG state.
- **Numbers become named buckets**, e.g. `"win_chance": "low"` or `"coins_vs_you": "far ahead"`. Never send numbers for Jev to compare.
- **Keep value types apart:** cash, expected sale value, benefit of keeping the team, risk and promises are separate buckets. They are never merged into one coin figure, and badges are never counted as coins.
- **Wording:** questions and criteria are written **in English**, literally, with boundary cases spelled out in the criteria.
- **One question = one decision.** Multi-item work is split into one question per item and combined in code.
- **Size:** state ≤ ~4k tokens per request.
  - At most the last 3 relevant chat messages, as quoted data with the speaker's name.
  - Memory is included as event evidence, e.g. "broke no_attack on turn 5".

### 5.5 Personality as a file

Each personality (Aggressive / Cautious / Greedy / Opportunist) has one `content/personalities/<name>.json` file containing:

- an English `description` inserted into instructions
- `weights` (risk, aggression, liquidity, loyalty) for the fallback policy, sell thresholds and shortlist filtering
- `lineStyle` for choosing lines

Decide it once in the file, and every build and every game follows it. The file is not tied to a betrayal percentage the AI must hit.

### 5.6 Difficulty, confidence and fallback

Every level uses the same observation.

| Level | How it chooses |
|---|---|
| Easy | The engine sends immediate effects only; the AI **samples from Jev's `probabilities`** (seeded and logged) |
| Normal | The engine adds buckets for distance to Start, Laps remaining, keep value and sale opportunity; the AI takes the **argmax** |
| Hard *(gate G2)* | The engine runs Monte Carlo rollouts from the belief state and sends expected-outcome buckets per option before the argmax. Unknowns are sampled from known information; it never reads the real deck or seed |

- **Confidence floor:** set per question type and option count, then tuned on the C4 eval set for `jev-1.13.0`.
  - Below the floor (Normal/Hard), the fallback policy chooses between Jev's top two by personality weight.
  - 0.6 is only the starting value for questions with few options.
  - Reason: the docs compute confidence as `(n·peak − 1)/(n − 1)`, so a 12-option Choice with a 0.6 peak scores ≈0.56. A fixed 0.6 floor would send most strategy calls to the fallback.
- **Deadlines:** 1,000 ms per request and 1,500 ms per decision. A retry is allowed only within the total budget.
- **Unusable answers:** timeout, 429, 5xx, a schema mismatch or a revision mismatch → fall back immediately. A late response is never applied after a fallback.
- **Metrics:** report `invalidOutputRate` and `fallbackRate` by cause, separately from `illegalAppliedActionCount`, which must be 0.
- **Numbers shown to players:** Jev's answer is a choice, not proof of correct calculation. Numbers and win results are shown from the engine only.

### 5.7 Dialogue

- **Files:** `content/lines/th/<situation>.json`, e.g. deal_accept, deal_reject, promise_kept, promise_broken, gym_win, taunt_leader, manipulation_refused, fallback_notice.
- **Coverage:** each situation has ≥3 lines per personality per trust bucket, with slots such as `{target}` or `{turn}` filled by the engine.
- **Selection:** Jev picks the line ID; when unavailable, a seeded random pick is used.
- *(Stretch, off by default)* A generative LLM may rephrase lines. It must pass the leak tests and stay off the critical path.

## 6. Architecture, data and replay

TypeScript plus a web app with API routes. The folders are `engine/`, `content/`, `ai/` (server), `web/`, `sim/` and `eval/`. No extra monorepo toolchain is required.

1. **`engine/`** has no IO. The same engine runs in the web app, sim and eval, and human and AI commands pass the same validation.
2. **`ai/`** is a server-side endpoint. It holds `TYPESAFE_API_KEY`, validates payload shape and size, builds questions from state, calls Jev and returns only action IDs and line IDs.
3. **Action records:** every action carries `actorId`, `actionSeq`, `stateRevisionBefore` and `payload`. `actionSeq` increments on every state change, including dice results and deal confirmations.
4. **Turn counters:** `globalTurnNo` counts turns and `ownTurnNo` counts each player's turns, both separate from `seatIndex`.
5. **Movement and Laps:** movement stores a signed `routeProgress` and a monotonic `creditedLap`.
   - Position = `((routeProgress % 24) + 24) % 24`.
   - Start credit is granted only when the owner's forward movement crosses a milestone above the previous `creditedLap`.
   - Being pushed or pulled, or re-crossing an old milestone, gives no reward.
6. **Instance IDs:** every Pokémon and item has its own instance ID.
7. **Save:** a local save after each accepted action.
   - It holds the current state plus the action log, with no log nested inside the snapshot, and no key.
   - Postgres/Docker are out of scope.
8. **Replay:**
   - Requires the full initialConfig, seed, `engineVersion`, `contentVersion`, the action log, and the random results used. Alternatively, the same RNG version with a verified cursor.
   - Jev answers that affect state are logged as events `{requestId, model, questionId, choice, probabilities, confidence, sampled, fallbackReason}`.
   - **Replay never calls Jev again.**
9. **Resume:** start from the last committed action. Pending requests are cancelled and re-asked from the same state.

## 8. Verify: four layers

Each layer covers what the one below misses.

| Layer | What | Deliverable and gate |
|---|---|---|
| **Tests** | Engine invariants, property-based tests over random legal action sequences, replay determinism | 100% pass in CI |
| **Eval set** | `eval/jev/`: ≥60 decision scenarios (15 per personality) with acceptable-answer sets; ≥80 chat-intent messages (50% Thai / 50% English); ≥30 adversarial items (prompt injection, probing for hidden info) | Report accuracy, calibration (confidence vs correctness) and personality separation; leaks = 0 |
| **Critic** | Exploit policies in sim: always PvP, force weak targets, sell everything every Start, keep everything to evolve, use Abilities immediately, buy only Ultra Balls, never negotiate. *(Stretch)* Expose the engine as MCP tools (`get_observation`, `list_legal_actions`, `apply_action`) so an LLM agent can hunt for exploits | No single policy dominates every context; report with n |
| **Human** | Playtest with 5–8 people, plus team review checkpoints on every rule change | Report issues and findings; no artificial thresholds |

**Engine invariants that must hold:**

- Coins never go negative, and every transfer has a source.
- UIDs are unique, and every creation or destruction is logged.
- Rejected or stale actions do not change state, and deals are atomic.
- Move debuffs last until the next move. Tired and Nurse Joy each have real use cases. Promises close on the correct `ownTurnNo`.
- Replay and resume never create assets or re-roll dice.
- Every catch attempt consumes exactly 1 Ball, and releasing consumes none.
- Abilities fire ≤1 per instance per Lap and ≤1 per player turn, and evolution does not reset cooldowns.
- Rescue Starters cannot create a coin loop.
- A Battle Reward gives coins or evolution, never both. Evolution is one stage at a time on the same UID.
- The game can finish after an AI failure with any number of AIs.

**Simulation:**

- **Game sets:** 1,000 policy-only games for bug hunting and trends, plus 300 Jev-in-the-loop games.
- **Variation:**
  - 2/3/4 seats, with class, personality and seat balanced across games.
  - Tuning seeds are kept separate from evaluation seeds.
  - Paired seeds are analysed as pairs.
- **Scoring:**
  - k co-winners score 1/k each, and the tie rate is reported.
  - Hostile items are reported as `hostileUsed / legalHostileOpportunity`, by personality and Lap.
  - Promises are reported as accepted / broken / kept-with-opportunity / kept-without-opportunity / closed-by-game-end, with `breachOpportunity`. If most promises have no chance to be broken, the system is only background decoration.
- **Difficulty:** show win/tie/loss, effect size, uncertainty and n. If Hard does not beat Normal, never add hidden information to make the graph pass.
- **Personality and chat:**
  - Personality: paired scenarios swap personality while holding everything else constant.
  - Chat: compare no-message / neutral / relevant-persuasion.
  - Memory: compare a history of kept promises with a history of broken ones.
  - Graphs from policies we configured ourselves prove only that the rules work, not that Jev understands relationships.

**Playtest:**

- Players play without every button explained, then answer:
  - Was there a moment you genuinely hesitated between selling and keeping?
  - Could you tell an opponent's personality from what it did?
  - Did any conversation change the game?
  - When did waiting or reading get boring?
- Record turn latency p50/p95, game length, drop-offs and the number of meaningful choices.

## 9. Control

**Money**

- **Estimate (to be measured in C1):** ~2,500 input tokens per request × ~140 requests per Standard 4-seat game ≈ 350k tokens ≈ **$0.015 per game**.
  - 300 games ≈ $4.4; 1,000 games ≈ $15.
  - That is about THB 150 and THB 500, at an assumed 33 THB/USD.
- **Limits:**
  - ≤3 requests per AI turn and ≤600k input tokens per game. Past that, the AI uses the fallback until the game ends.
  - A daily budget on the development key.
  - A **total cap of THB 1,500**, tracked from the usage log.
- **Kill switch:** `JEV_ENABLED=false` puts every AI on the fallback, and the UI says so truthfully.
- **Sim limits:** max steps per game, and concurrency ≤10 requests/s, well under the rate limit.

**Safety (least privilege)**

- The key lives only on the server: never in the browser, saves, logs, or a coding agent's sandbox.
- Jev reads one role's observation and can answer only with IDs from the options, so it cannot modify state.
- Chat is length-limited, sent as quoted data, and screened by the manipulation Noul. A message that fails never enters any decision's state. The adversarial set is a gate before free text is enabled.
- No personal data about players is stored; playtests use codes instead of names.

**Who is in charge**

- The engine is the sole rules authority; Jev and the fallback only choose.
- The human confirms their own deals.
- The team owns the spec. Coding agents propose through PRs, and people merge.

## 11. An honest demo

1. Open setup and choose 1–3 AIs with class and personality.
2. Load a demo scenario announced as prepared, and show two legal options.
3. The AI chooses a Ball/Ability/Item, with a "What Jev chose" panel showing the options, probabilities and confidence. The actual result comes from the engine.
4. Issue a PvP challenge and show the accept or decline, or a rule-based force.
5. Win, choose coins or evolution, and show the new form's stats and Ability.
6. Show memory from a kept or broken promise and its effect on negotiation.
7. Flip the kill switch; the game continues on the backup bot with a visible badge.
8. Show graphs separating policy-only from Jev: n, latency, fallback rate, actual spend and limitations.

The prototype succeeds when players enjoy the decisions, feel that each opponent plays differently, and the rules remain auditable.
